# プロジェクト初期計画スキル

ユーザーと対話しながらプロジェクトの要件・背景・優先度を整理し、`docs/initial-plan/` 配下に構造化されたドキュメント群を出力する。

## 基本原則

- **質問は一度に2〜3問まで**にし、回答を受けて次の質問を組み立てる
- 曖昧な回答には**深掘り質問**で具体化する（「例えば？」「もう少し具体的に教えてください」）
- ユーザーが「分からない」と言った場合は無理に聞かず、仮置きとしてマークして先に進む
- 全フェーズを通じて **Must（必須）と Nice-to-have（あると嬉しい）の区別** を意識し、ユーザーにも判断を促す
- ヒアリングの各フェーズで得た情報は内部的にメモし、最終出力に漏れなく反映する
- ユーザーの回答に応じてフェーズの順番や深さを柔軟に調整する

---

## フェーズ 1: プロジェクトの全体像

まずプロジェクトの大枠を掴む。以下の質問をベースに対話する:

1. **何を作りたいですか？** — プロダクト/サービスの概要を一言で
2. **なぜ作りたいのですか？** — 動機・背景・解決したい課題
3. **誰が使いますか？** — ターゲットユーザー、利用シーン

回答が抽象的な場合の深掘り例:
- 「それは既存の〇〇とはどう違いますか？」
- 「具体的なユースケースを1つ教えてもらえますか？」
- 「最初の1人のユーザーを想像すると、どんな人ですか？」

---

## フェーズ 2: 機能と要件

コア機能を洗い出す。

1. **このプロダクトで一番大事な機能は何ですか？** — これがないとユーザーが使わない機能
2. **他にどんな機能を考えていますか？** — 思いつく限りリストアップしてもらう
3. **それぞれの機能について、初回リリースに必須ですか？それとも後で追加でもいいですか？**

各機能を以下のMoSCoW分類に振り分ける:
- **Must（必須）**: 初回リリースに絶対必要
- **Should（重要）**: あった方がいいが、なくても最低限動く
- **Could（あると嬉しい）**: 余裕があれば
- **Won't（今回はやらない）**: スコープ外と明示

分類結果をユーザーに提示し、合意を取る。合意が取れるまで調整を繰り返す。

---

## フェーズ 3: 技術的な制約と希望

1. **使いたい技術スタック（言語、フレームワーク等）はありますか？** — 指定がなければ要件に基づいて候補を提案する
2. **デプロイ先の希望はありますか？** — クラウド、オンプレ、特定サービス等
3. **外部サービス連携はありますか？** — 認証、決済、API等
4. **非機能要件で気にしていることはありますか？** — パフォーマンス、セキュリティ、可用性等

---

## フェーズ 4: デザインとUX

**注意: UIが不要なプロジェクト（CLI、API、ライブラリ等）はこのフェーズをスキップする。**

1. **UIのイメージはありますか？** — 参考サイト、ワイヤーフレーム、手書きスケッチ等
2. **対応デバイスは？** — PC、スマホ、タブレット
3. **デザインで重視することは？** — シンプルさ、情報密度、アクセシビリティ等

---

## フェーズ 5: スケジュールと優先順位

1. **期限やマイルストーンはありますか？**
2. **最初に動くものを見たい時期は？**（MVP）
3. **開発に関わる人数は？**

---

## フェーズ 6: 補足と確認

1. **他に伝えておきたいこと、気になっていることはありますか？**
2. これまでのヒアリング内容を以下の形式でサマリーし、ユーザーに最終確認を取る:

```
## ヒアリングサマリー

**プロジェクト概要**: {1〜2文}
**ターゲットユーザー**: {誰が・どんな状況で}

**機能（Must）**:
- {機能1}
- {機能2}

**機能（Should）**:
- {機能1}

**機能（Could）**:
- {機能1}

**スコープ外（Won't）**:
- {項目}

**技術スタック**: {言語、フレームワーク等}
**制約事項**: {あれば}
**スケジュール**: {あれば}
```

**修正があれば反映し、再度確認する。合意が取れるまで繰り返す。ファイル生成は合意後に行う。**

---

## フェーズ 7: ドキュメント生成

合意が取れたら、以下のファイルを `docs/initial-plan/` 配下に生成する。
情報がないセクションは省略し、空セクションを残さない。
ヒアリングで「分からない」とされた項目は `open-questions.md` に記載する。

### 生成ファイル一覧

| ファイル | 内容 |
|---------|------|
| `README.md` | ドキュメント目次とプロジェクト概要 |
| `overview.md` | ビジョン、背景、ターゲットユーザー、スコープ |
| `requirements.md` | 機能要件（MoSCoW分類）+ 非機能要件 |
| `architecture.md` | 技術スタック、システム構成、ディレクトリ構成案 |
| `milestones.md` | MVP定義、フェーズ分け、マイルストーン |
| `open-questions.md` | 未決事項、要調査項目、仮置きした判断 |

### 各ファイルの構成

**README.md:**
```markdown
# {プロジェクト名} — 初期計画

## このドキュメントについて
ヒアリングを基に作成した初期計画ドキュメント群。

## ドキュメント一覧
- [プロジェクト概要](./overview.md)
- [要件定義](./requirements.md)
- [アーキテクチャ](./architecture.md)
- [マイルストーン](./milestones.md)
- [未決事項](./open-questions.md)
```

**overview.md:**
```markdown
# プロジェクト概要

## ビジョン
{プロジェクトの目指す姿}

## 背景と動機
{なぜこのプロジェクトを始めるのか}

## 解決する課題
{ユーザーが抱える具体的な課題}

## ターゲットユーザー
{誰がどのような状況で使うか}

## スコープ
### 今回やること
- {項目}

### 今回やらないこと
- {項目と理由}
```

**requirements.md:**
```markdown
# 要件定義

## 機能要件

### Must（必須）
- [ ] {機能名}: {説明}

### Should（重要）
- [ ] {機能名}: {説明}

### Could（あると嬉しい）
- [ ] {機能名}: {説明}

### Won't（今回はやらない）
- {機能名}: {理由}

## 非機能要件
- {カテゴリ}: {要件}
```

**architecture.md:**
```markdown
# アーキテクチャ

## 技術スタック
| カテゴリ | 技術 | 選定理由 |
|---------|------|---------|
| {カテゴリ} | {技術名} | {理由} |

## システム構成
{構成の説明}

## 主要コンポーネント
### {コンポーネント名}
- 責務: {説明}

## 外部サービス連携
- {サービス名}: {用途}
```

**milestones.md:**
```markdown
# マイルストーン

## MVP（最小限の動くもの）
- 目標時期: {時期}
- 含まれる機能:
  - {機能}

## Phase 1: {フェーズ名}
- 期間: {期間}
- ゴール: {何ができるようになるか}
- タスク:
  - [ ] {タスク}
```

**open-questions.md:**
```markdown
# 未決事項・要調査項目

## 未決事項
| # | 項目 | 背景 | 仮の判断 | 期限 |
|---|------|------|---------|------|
| 1 | {項目} | {なぜ未決か} | {暫定案} | {いつまでに決めるか} |

## 要調査項目
- [ ] {調査内容}: {なぜ必要か}

## 補足メモ
- {カテゴリに収まらなかった情報}
```

## フェーズ 8: 最終確認

生成したファイル一覧をユーザーに報告し、内容を確認してもらう。修正依頼があれば対応する。
